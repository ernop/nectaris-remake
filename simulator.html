The Rust simulator

You play the JavaScript game in your browser. On the development machine, a Rust copy of the same game runs the rules and all five computer opponents much faster, for tournaments, tests and experiments with new AI players.

The two versions are kept in lockstep: the same rules, the same dice, the same legal moves, and the same choice by every bot in every position. A change to one must land in both, and the checks listed below enforce that on every push.

Fair dice

Every match rolls its own dice: ChaCha20, a cryptographic stream cipher, keyed by a 256-bit seed. However many rolls a player or bot has seen, the next one cannot be predicted without the seed. A match with no seed, which includes every game in the browser and every tournament run started without one, draws a fresh seed from the operating system's random source. A given seed, such as 42, is stretched to 256 bits with SHA-256, so even a short seed cannot be searched.

No bot sees the dice. Bots imagine battles with their own separate generator, seeded from the public position. In Rust the dice cannot be reached from bot code: only the engine's attack rolls them, and only the state fingerprint can read them. In JavaScript a test plays tournament games with every bot and fails if anything other than an attack rolls the match's dice, or if anything reads them while a bot is thinking.

A tournament records its seed, so its games can be replayed exactly. It draws a fresh seed unless given one.

How we check that both versions match

The checks compare whole games, not samples of single rules. They start from 58 recorded games (16,893 commands) on boards from every family: Classic against Tactical played to the end, and short games of Sequence, Simulation, Apex and Marshal. Checks marked "Every push" run in GitHub's test workflow, and a failure holds the release of the live site.

The fingerprint is text built from everything that affects future play: the turn, the side to move, the winner, the dice's position, every unit's type, side, place, strength, experience, remaining movement, action flags and cargo, and every building's owner and stored units.

It includes the dice's position because both versions draw one roll per shot from the same seeded dice. If one of them drew an extra roll, the board could look identical while every later battle came out differently. With the dice's position in the fingerprint, the check fails at the exact command where it happened.

Using it

The simulator lives in sim/ and needs Rust from rustup. From that folder:

cargo run --release -- tournament --out=/tmp/league --opponents=classic,tactical,beam,monte-carlo,apex --boards=0,1,2 --cycles=10
node ../tools/sim/import-rust.cjs /tmp/league
cargo run --release -- playout --games=4000
cargo run --release -- replay
cargo run --release -- decide --verify-caches

The import step checks every game in JavaScript and writes an archive; each game file opens in the Bot tournament page's replay viewer. For long runs, tools/sim/build-pgo.sh builds the profile-guided binary, checks it against the recorded games, and prints its path. It needs rustup's llvm-tools component. New AI players plug into the engine through two interfaces: one plays whole turns, the other picks one command at a time from the legal-move list. Before the browser offers a new player, it needs a JavaScript twin that decides identically.

Measured on 27–29 September 2026 on an AMD Ryzen 9 5950X (16 cores, 32 threads) with Node 22 and Rust 1.98. More detail on GitHub: the simulator's plan and measurements and running tournaments.
